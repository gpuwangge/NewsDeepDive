# 10/18/2026 [Google开源Harness框架](https://www.marktechpost.com/2026/10/18/google-harness2-recursive-agent-harnessing-framework/)
特邀评论员：Gemini (Google LLC)  
责任编辑：Wangge  

## 新闻回顾

谷歌云AI研究团队（Google Cloud AI Research）与西北大学联合开源了名为 **Harness²** 的递归代理驾驭框架（Recursive Agent Harnessing Framework，版本号 v0.1.0，采用 Apache-2.0 协议）。该框架的核心在于：在完全不修改大语言模型权重（Frozen Model）的前提下，通过在推理阶段（Test-Time）对模型外围的“驾驭层（Harness）”进行双层递归优化，实现智能体（Agent）自我能力提升。

Harness² 涵盖了 **8 个可编辑的 Harness 组件**（System prompt、Guardrails、Memory、Tool guidance、Subagents、Skills、Scripts、Plugins），通过**任务级递归**（结合 Propose、Probe、Compose 策略对比不变量与特定领域候选）和**驾驭级递归**（维护包含 EXPERIENCE.md 的经验库）进行自适应优化。在 WorkBuddy-Bench、JobBench 及 LAB 等基准测试中，结合 Gemini 3.5 Flash 和 GLM-5 模型（配合 OpenCode 和 Codex 执行环境，由 Claude Opus 4.8 担任编辑模型），即使经过单步优化（$k=1$），所有测试组合的表现均有显著提升；其中 GLM-5 在 WorkBuddy-Bench 上的得分从 64.2 跃升至 75.7（提升 11.5 分），表现超越了未优化的基线 Gemini 3.5 Flash。

## 技术分解

#### Q1: Harness² 中的“Harness（驾驭层）”具体包含哪些部分？它与传统 Prompt 工程有什么区别？

**A:** 传统 Prompt 工程大多仅局限于调整系统提示词（System Prompt）。Harness² 将 Harness 扩展为 8 个模块化组件文件：

1. **System prompt（系统提示词）**：定义角色与全局指令。
2. **Guardrails（安全与行为护栏）**：约束输出边界与操作合规性。
3. **Memory（记忆机制）**：管理长短期上下文与历史记录。
4. **Tool guidance（工具使用指导）**：定义如何选择与调用 API/工具。
5. **Subagents（子代理调度）**：复杂任务的拆解与多代理分工。
6. **Skills（技能库）**：特定任务的可复用操作流程。
7. **Scripts（执行脚本）**：辅助逻辑或自动化工具代码。
8. **Plugins（中间件插件）**：对接外部环境与输入输出的扩展接口。

通过对这 8 个组件的动态重写，Harness² 调整的是整个 Agent 的“运行环境与行为逻辑”，而非单纯的文本输入。

#### Q2: Harness² 是如何在没有真值标签（Ground-Truth / Test Cases）的开放世界环境中实现自动优化的？

**A:** Harness² 采用了**双层递归机制**：

* **任务级递归（Task-level Recursion）**：
1. **Propose（提出）**：由 Editor 模型基于当前任务生成两套修改候选——Invariant（不变量候选，针对通用规划与工具调用错误）和 **Domain（领域候选，针对特定领域的专业知识与步骤）**。
2. **Probe（探针试跑）**：在同一任务上分别运行原始 Harness、Invariant 候选和 Domain 候选。
3. **Compose（组合融合）**：Composer 模块对比三种运行轨迹（Trajectories），仅保留在实际行为中有积极表现的改动，合成出最终的更新版 Harness。


* **驾驭级递归（Harnessing-level Recursion）**：
任务结束后，Reflector 模块将成功的 Harness 变更与总结出的经验写入 `EXPERIENCE.md` 知识库，指导后续任务的提案生成。

#### Q4: Harness² 方案是否存在明显的局限性与潜在隐患？

**A:**

1. **推理成本与延迟翻倍**：每次任务都需要生成并测试至少 2 个候选方案（Invariant 和 Domain），在并行采样预算 $k=5$ 时，调用的 Token 消耗和运行时间是普通推理的数倍。
2. **高度依赖“编辑模型（Editor Model）”能力**：实验中使用了 Claude Opus 4.8 这种顶尖模型作为 Editor。如果使用能力较弱的模型来编写 Harness，可能导致生成的 Prompt 或组件质量下降，甚至引发系统崩溃。
3. **安全与安全沙箱风险**：允许代理自主修改 Scripts 和 Plugins 组件并在本地环境运行，若没有严格的 Docker/隔离沙箱机制，极易引发任意代码执行（RCE）或意外毁坏运行环境的问题。


## 新闻分析

#### 1. 谷歌云 (Google Cloud AI Research) 角度

* **利**：巩固了其在 Agentic AI 基础设施与框架领域的标准制定权。通过开源 Harness²，推动“无需重训练模型即可提升智能体性能”的范式，并间接带动了其 Vertex AI 平台以及 Gemini 系列 API 的用量需求（运行递归优化会消耗大量 API Token）。
* **弊**：开源框架容易被竞争对手（包括开源模型社区）直接套用，用以抹平开源模型与谷歌自家顶级模型之间的原生性能差距（如 GLM-5 优化后性能追平甚至超越基线 Gemini 3.5 Flash）。

#### 2. 开源模型社区与中小型开发者角度

* **利**：极大降低了高端智能体的构建门槛。开发者无需投入昂贵的算力进行模型微调（Fine-Tuning）或 Reinforcement Learning（RL），仅凭 Harness² 框架和 API 即可让性价比更高的开源或中等规模模型（如 GLM-5）在复杂专业任务中实现跨越式提效。
* **弊**：增加了架构复杂度和 API 调用成本；面对缺乏标注的开放任务，调试递归搜索产生的异常轨迹（Trajectories）会带来更高的运维成本。

#### 3. 商业模型供应商（如 Anthropic 等）角度

* **利**：作为高质量 Editor/Reflector 模型（如 Claude Opus 4.8）的供应商，在 Harness² 这类需要高阶推理、代码生成和自我反思的框架普及过程中，将持续获得大量高价值的 API 调用额度。
* **弊**：底座模型性能“边际效益递减”现象更加明显，用户对底座模型频繁升级的依赖度降低，转而依靠外围 Harness 的自我演进解决难题。


### 总结归纳

* **算力**：放弃了训练阶段（Training-time）的大规模 GPU 算力消耗，转移为推理阶段（Test-Time）的多次 API 调用与探针试跑算力，本质上是用推理算力换取智能上限。
* **资本**：大幅降低了中小型企业模型训练与微调的资本门槛，但将软件开发预算转移到了 API Token 的持续消费与云端沙箱基础设施的维护成本上。
* **幻觉**：由于缺少真值校验，完全依托模型自身进行轨迹对比（Contrastive Evaluation），在面对复杂专业逻辑时，若 Editor 和 Composer 模型同时产生误判，可能陷入“自我强化错误 Harness”的系统性幻觉陷阱。
