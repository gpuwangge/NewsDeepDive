# 09/17/2026 [华为发布Atlas 960E SuperPoD](https://www.huawei.com/en/news/2026/9/hc-ascend960-supernode)
特邀评论员：Perplexity(Perplexity AI, Inc)  
责任编辑：Wangge  

## 新闻回顾

华为在上海举办的 HUAWEI CONNECT 2026 上发布 **Atlas 960E SuperPoD**，将其定义为业界首个基于 **NPO（Near-Packaged Optics，近封装光学）** 的 SuperPoD，目标是支持十万亿参数级基础模型的训练和推理。

核心技术组合包括：

- **Ascend NPU**：单个 Atlas 960E SuperPoD 可扩展至 **4,096 个 NPU**。
- **UnifiedBus**：统一协议、点对点互连及统一内存寻址，使跨物理服务器的内存访问成为系统设计的一部分。
- **Hi-ONE 光引擎**：华为量产化 NPO 光互连产品，单引擎传输能力 **7.2 Tbit/s**，并集成光源。
- **正交网络架构**：Atlas 960E 使用正交互连与全液冷设计，服务高密度 AI 集群部署。
- **性能指标**：华为声称单 SuperPoD 提供 **8 EFLOPS FP8** 或 **16 EFLOPS FP4** 算力。
- **光模块替代**：系统集成约 **5,500 个 Hi-ONE**，据称可省去传统方案中约 **48,000 个 800G 光模块**，功耗减少超过 **550 kW**。
- **可靠性**：华为宣称系统可达到 **99.8% 可用性**，并使无故障运行时间翻倍。
- **超集群扩展**：多个 Atlas 960E 可通过 UnifiedBus 或 RoCE 连接；双层四平面 Clos 网络最大可互连 **512,000 个 NPU**，叠加 multi-rail 拓扑时可支持至多 **100 万个 NPU**。
- **通用计算扩展**：华为同步升级 TaiShan 950 SuperPoD，以 UnifiedBus 全光网络连接最多 4,096 个节点，统一内存池最高 **256 TB**。
- **存储扩展**：OceanStor M900 被定位为面向上下文记忆的存储集群，提供 PB 级 KV Cache，并声称支持一跳直连访问。
- **软件生态**：华为宣布 **CANN** 进入持续、社区驱动的开源开发阶段，试图把 Ascend 软件栈从“可用”推进至“更易用”。 [huawei](https://www.huawei.com/en/news/2026/9/hc-ascend960-supernode)

## 技术分解

### Q1：NPO 是什么，为什么它是这则新闻的关键？

**NPO** 是 Near-Packaged Optics，即将光学互连模块部署在靠近交换 ASIC、计算芯片或高速 SerDes 的位置，而非完全依赖插拔式前面板光模块。

传统 800G/1.6T 数据中心网络大致是：

交换芯片 → 长距离板级电走线 → **可插拔光模块** → 光纤

NPO 的思路则是：

交换芯片 → 短距离高速电连接 → **近封装光引擎** → 光纤

其主要价值在于降低高速电通道损耗。随着每通道速率从 112G PAM4 继续走向 224G PAM4，传统 PCB 走线、连接器、Retimer 以及可插拔模块间的电损耗与功耗都会急剧变得更难控制。NPO 将光电转换点前移，通常可以减少高频电信号的传输距离。

华为称 Hi-ONE 单个光引擎可提供 7.2 Tbit/s 带宽，并且集成光源；这意味着它不仅是一个外置光模块，而是面向高密度交换互连的光电系统级部件。

### Q2：Atlas 960E 的 4,096 NPU 和 16 EFLOPS FP4 意味着什么？

华为公布的关键集群规模与算力是：

| 指标 | Atlas 960E SuperPoD 宣称规格 | 工程意义 |
|---|---:|---|
| NPU 数量 | 4,096 | 单 Pod 已达到超大规模训练集群级别 |
| FP8 总算力 | 8 EFLOPS | 面向训练、混合精度推理及较高数值稳定性需求 |
| FP4 总算力 | 16 EFLOPS | 面向低比特推理或低精度训练路径 |
| 光引擎数 | 5,500 个 Hi-ONE | NPO 被视作系统规模化的关键部件 |
| 替代光模块 | 约 48,000 个 800G 模块 | 试图降低前面板模块密度、功耗与布线复杂度 |
| 降低功耗 | 超过 550 kW | 集群网络层的能耗优化，而非整个数据中心能耗 |
| 系统可用性 | 99.8% | 对应约每年 17.5 小时不可用时间，实际定义仍需明确 |
| 扩展规模 | 512,000 至 1,000,000 NPU | 属于互连拓扑宣称上限，非等同于单一模型可高效率利用的规模 |

若按华为公布的聚合数字平均拆算：

\[
\frac{8\ \text{EFLOPS FP8}}{4,096} \approx 1.95\ \text{PFLOPS FP8/NPU}
\]

\[
\frac{16\ \text{EFLOPS FP4}}{4,096} \approx 3.91\ \text{PFLOPS FP4/NPU}
\]

这说明华为瞄准的并不是一般企业推理服务器，而是与全球前沿 AI 集群相同量级的高密度训练与推理基础设施。

但应注意：峰值 FLOPS 不是模型训练吞吐量。真正决定大模型训练效率的，还包括：

- 单卡 HBM 容量、带宽和实际可用容量。
- NPU 间互连的单向/双向带宽、延迟、拥塞控制与集体通信效率。
- TP、PP、EP、DP 等并行策略的可扩展性。
- MoE All-to-All 通信效率。
- 算子库、编译器、图优化及训练框架适配程度。
- 节点故障处理、检查点恢复速度和作业调度效率。

因此，16 EFLOPS FP4 是一个重要的硬件定位信号，但尚不足以推导出它在具体模型、特定 batch size 或特定训练配方下必然优于其他 AI 集群。

### Q3：UnifiedBus 与传统 RoCE 或 InfiniBand 的差异是什么？

从华为的描述看，**UnifiedBus** 试图将系统从“由多个服务器和网络设备构成的集群”推进到“具有统一地址和统一互连抽象的计算池”。

| 维度 | UnifiedBus 的目标定位 | RoCE | InfiniBand |
|---|---|---|---|
| 核心抽象 | 跨节点统一互连和内存访问 | 基于以太网的 RDMA | 专用高性能 RDMA 网络 |
| 内存语义 | 强调统一内存寻址和跨服务器访问 | 一般需要显式注册、RDMA 操作与软件管理 | 高性能消息传递与 RDMA |
| 网络依赖 | 华为自有系统级架构 | 标准以太网生态 | 专有网络生态，软硬件协同紧密 |
| 扩展目标 | SuperPoD 与 SuperCluster | 云数据中心、企业集群、AI Fabric | 高性能计算和大规模 AI 训练 |
| 最大挑战 | 软硬件生态、可观测性、互操作性 | 网络调优和拥塞控制 | 供应商锁定、成本和生态集中度 |

UnifiedBus 的工程吸引力在于：若跨节点内存访问能拥有足够低的延迟、高的有效带宽和良好的隔离机制，模型状态、KV Cache、专家参数、Agent sandbox 以及上下文存储可以被以更统一的方式调度。

但这里要保持批判性：新闻没有给出 UnifiedBus 的关键性能参数，包括端到端延迟、每端口带宽、bisection bandwidth、拥塞控制机制、传输层语义、故障域、缓存一致性模型，以及与 PyTorch 分布式训练或主流通信库之间的实际映射。因此，现阶段更适合把它视为一种系统架构方向，而非仅凭“统一内存寻址”就认定其效果已等价于本地 HBM 或高质量的全局共享内存。

### Q4：用 5,500 个 Hi-ONE 替代 48,000 个 800G 光模块，优势在哪里？

华为的核心叙事是：将大量可插拔 800G 光模块替换为更靠近交换芯片的 NPO 光引擎，可显著减少光互连链路中的电损耗和相关功耗。

可能的优势：

- 减少高速电信号从交换芯片到前面板模块之间的传输距离。
- 降低 SerDes 驱动、重定时器和长距离 PCB 走线带来的功耗压力。
- 降低大规模光模块密度带来的气流、散热、布线和维护复杂度。
- 在全液冷系统中，可以更系统地整合计算、交换与光电互连散热。
- 通过更少的互连部件和更短链路，理论上改善故障率和系统可用性。

但 NPO 并非没有成本：

| NPO 潜在收益 | NPO 现实挑战 |
|---|---|
| 更低电功耗和更高端口密度 | 光引擎更接近核心芯片，现场维护与更换难度上升 |
| 有利于 224G 及更高速率演进 | 封装、机械、热设计、EMI 与光学耦合协同难度极高 |
| 降低前面板可插拔模块数量 | 失去可插拔光模块带来的灵活部署与快速替换能力 |
| 可能提高网络可靠性 | 光源、激光器寿命与冗余设计需要长期运行验证 |
| 适合超大规模同构 AI Fabric | 不一定适合中小型、异构或频繁改造的数据中心 |

尤其值得注意的是，华为宣称 Hi-ONE 为“唯一内置光源的 NPO”。内置光源可减少外部光源分配架构的复杂度，但也把激光器可靠性、热漂移控制与故障更换问题带到更接近核心计算和交换硬件的位置。其长期 MTBF、故障定位方式、可维护性和整机 RMA 策略，仍是实际部署时必须验证的问题。

### Q5：为什么 TaiShan 950、OceanStor M900 和 Agent sandbox 也很重要？

这部分反映华为并不只想销售 NPU，而是在构建一个面向 Agentic AI 的完整基础设施栈：

- **Atlas 960E**：承担大模型预训练、后训练与高吞吐推理。
- **TaiShan 950 SuperPoD**：承担通用 CPU 计算、Agent 执行环境、工具调用服务与高密度 sandbox。
- **OceanStor M900**：承担 PB 级 KV Cache、上下文记忆、检索结果和长期状态数据。
- **CANN**：承担 Ascend 硬件的软件栈、编译、算子、运行时与框架接入。

AI Agent 的实际工作负载不只是矩阵乘法。它还包括并发会话、检索、向量搜索、代码执行 sandbox、浏览器自动化、缓存复用、数据库访问和多轮上下文维护。华为用 TaiShan 和 OceanStor 补齐 CPU、内存与存储侧，说明其目标是把“模型训练集群”扩展为“企业级智能体工厂”。

批判点是，Agent workload 是否需要“跨 4,096 节点统一内存池”仍取决于具体软件架构。很多生产系统更适合采用分片 KV Cache、局部性优先调度、分布式缓存和显式数据复制，而不是广泛依赖远端内存访问。统一内存抽象能够降低编程复杂度，却可能掩盖延迟、拥塞和数据局部性问题。

### Q6：CANN 开源，是否足以挑战 CUDA 生态？

CANN 的开源是华为争夺 AI 开发者的重要动作。若没有成熟软件栈，再强的 NPU 和互连都难以被大规模采用。华为称 CANN 已转向持续、社区驱动的开源开发模式。 

| 维度 | CANN 的机会 | 仍需验证的部分 |
|---|---|---|
| 硬件适配 | 对 Ascend NPU 有原生优化空间 | 软硬件代际兼容、性能回归和调试工具成熟度 |
| 开源策略 | 降低开发者进入 Ascend 的门槛 | 开源范围、治理方式、外部贡献接受度 |
| 中国本土生态 | 适配国产模型、云厂商与行业客户 | 跨地域开发者社区规模和全球 ISV 支持 |
| 框架接入 | 可服务 PyTorch、MindSpore 等路径 | 新模型、新算子和新训练技术的跟进速度 |
| 替代价值 | 为受供应链限制的用户提供选择 | 是否形成足以降低 CUDA 迁移成本的完整工具链 |

CUDA 的壁垒并不只是 API 本身，还包含多年累积的性能库、Profiler、Debugger、集群通信、部署工具、教程、论文复现代码、模型仓库和开发者心智。CANN 开源是必要条件，但不是充分条件；决定成败的关键会是开发者是否能以低迁移成本稳定运行主流模型，并获得可预测的性能与运维体验。

## 新闻分析

### 华为的角度

华为在这则新闻中展示的是一条明确的纵向整合路线：从 Ascend NPU、光引擎、互连、服务器、存储、CPU、液冷，到 CANN 软件生态，覆盖 AI 基础设施的关键层次。

**收益：**

- 通过 NPO 与 UnifiedBus 差异化，避免在单芯片制程、HBM 供给或通用 GPU 软件生态上进行完全同质化竞争。
- 在高端 AI 硬件受外部供应限制的背景下，提供本土化、系统级的替代选择。
- 以 SuperPoD 为产品单位，提高硬件销售客单价，并绑定网络、存储、运维和软件服务。
- 将“万卡集群”叙事扩展为百万 NPU 的 AI 基础设施叙事，强化其面向国家级云、运营商和大型企业的定位。
- CANN 开源可扩大开发者触达面，降低客户对单一闭源平台的担忧。

**风险：**

- NPO、液冷、超大规模互连与统一内存都是高复杂度系统工程；任何一个环节的良率、可维护性或软件稳定性问题都可能放大到集群层面。
- 发布的 FP4/FP8 峰值、节电和可用性数据主要来自厂商口径，尚缺少公开第三方基准、长期生产负载数据和模型训练结果。
- 一百万 NPU 的网络拓扑可连接规模，不等于一百万 NPU 可被单一训练作业高效率利用；通信、同步、容错与数据管道会成为更硬的约束。
- 生态建设需要长期投入。若主流开源模型、训练框架和推理引擎不能快速原生支持 Ascend，硬件价值会受到限制。

### 中国云厂商与大型企业的角度

对于希望扩张 AI 算力、同时降低外部 GPU 供应不确定性的云厂商、运营商、金融机构和政企客户，Atlas 960E 代表了一个更完整的国产化 AI 基础设施候选方案。

**收益：**

- 可获得从训练、推理、存储到 Agent 运行环境的一体化平台。
- 在采购、供应链与合规层面拥有更多选择。
- 通过高密度互连、液冷和功耗优化，可能降低大规模集群的总拥有成本。
- 若 CANN 与主流框架适配成熟，可减少单一海外 GPU 平台的依赖。

**风险：**

- 从 CUDA/NCCL/PyTorch 生态迁移需要重做算子验证、性能调优、模型精度测试和生产工具链集成。
- NPO 系统的光学部件维修、备件策略、现场故障定位和扩容灵活性，将显著影响实际运维成本。
- 若核心组件供应、软件版本与硬件迭代深度绑定，客户可能从一种生态锁定转向另一种生态锁定。
- 企业不能只看峰值算力，应要求给出特定模型的 tokens/s、训练 MFU、MoE 通信效率、P99 延迟、能耗/Token 和故障恢复时间等数据。

### NVIDIA、AMD 与其他 AI 芯片厂商的角度

华为的路线并不只是在复制 GPU 集群，而是在光互连、系统拓扑、存储和 Agent 基础设施层面进行竞争。这会加剧 AI 基础设施的竞争重心从“单卡算力”转向“整机柜、整 Pod、整集群可交付能力”。

**对 NVIDIA 的影响：**

- 华为强化了“非 CUDA AI 基础设施”的市场叙事，尤其在中国市场。
- NPO 和高密度光互连方向与全球 AI 数据中心的发展需求一致，促使竞争者进一步加速网络、光学和机柜级系统创新。
- 但 NVIDIA 仍拥有更成熟的软件生态、广泛的框架支持和实际规模部署经验；华为要削弱这种优势，需要在开发体验与真实工作负载性能上持续证明自己。

**对 AMD、Intel、网络芯片与光模块厂商的影响：**

- AI 集群竞争正把价值链推向高速 SerDes、光电共封装/近封装、液冷、交换芯片、存储和集群软件。
- 若 NPO 大规模落地，传统可插拔光模块的结构性需求可能受到部分替代，但短期内二者更可能并存：可插拔方案仍具备模块化、可维护性与灵活布线优势。
- 对网络和光学供应商而言，最大的机会来自 800G 向 1.6T、3.2T 乃至更高速率演进；最大的挑战则是封装集成度提升可能重塑利润池和供应链位置。
